# Xaibo design delta 1 — proposed

## 1. Summary

- **Status: proposed, 2026-11-14.** D-P4-03(b); Claude review, then owner approval, are required before adoption.
- The locked system is [xaibo-design.md](../xaibo-design.md), approved at Gate D; its older draft/pending wording does not supersede the owner's approval.
- Modern-web-guidance supports the existing native controls, bounded rendering, plain-text content, focus, reflow and reduced-motion choices.
- Hallmark's permitted floor/reflex/lint lens supports the ruled ledger; its marketing-page defaults must yield to the brief.
- UI UX Pro Max is available and was applied through its local UX, web and chart rules; a replacement design system was not generated.
- **Seven proposals: 2 must, 4 should, 1 could.** “Must” identifies a gap to settle before the affected interaction ships, not authority to implement this draft.
- No proposal changes a token, color, semantic foreground/background combination, navigation destination or phase boundary; all 54 existing contrast checks pass.
- This is a document review with local calculations, not a rendered UI, automated accessibility, runtime or performance certification.

## 3. Contrast and token impact

There are **no proposed color changes, token-value changes, token additions or new meaningful foreground/background pairs**. Updated §8.2 pair rows: **none**. In particular, proposals do not introduce error fills, modal dimming, disabled opacity, focus shadows or new semantic backgrounds.

As a read-only baseline check, all 27 inventory rows were independently recomputed in both themes from the design's literal sRGB hex values using §8.2: normalize each channel, linearize at 0.04045, calculate luminance with weights 0.2126/0.7152/0.0722, then divide lighter luminance + 0.05 by darker luminance + 0.05. Thresholds were tested before rounding. **54/54 checks pass**, and all published ratios match to 0.01.

| Existing category | Lowest light ratio | Lowest dark ratio | Required |
|---|---:|---:|---:|
| Text (18 pairs per theme) | 5.34:1, muted/tint | 6.48:1, danger/tint | ≥4.5:1 |
| Boundary/glyph (3 pairs per theme) | 3.23:1, line/tint | 4.09:1, line/tint | ≥3:1 |
| Focus/chart aliases (6 rows per theme) | 6.64:1 | 7.04:1 | ≥3:1 |

These calculations verify the specified inventory, not computed colors in an implemented screen. A later implementation that changes a token or introduces a pair still requires explicit updated rows, both-theme calculations, tests and review.

## 5. Items for the implementation (not design changes)

These carry forward existing requirements or verification work. They do not authorize code edits as part of this delta.

- **P4-T04, icons and frame:** replace coverage/finding Unicode icon substitutions with the existing §4 inline SVG geometries and visible words; apply the same rule to health glyphs. Build §6.0 native-title-bar layout, wrapping navigation, collection band and 24/16 px main padding. These are already specified; no new icon set or geometry proposal is needed.
- **P4-T04/P4-T05, list behavior:** enforce the existing three-page cache and Load previous, four-slice bound per open item, New activity available, focus/pointer reorder hold, primary Open control and CSP-safe CSSOM offsets. Keep the existing primitive; the brief's completed primitive is not proof of every consumer contract.
- **P4-T04/P4-T13, hidden window:** use the app's explicit hide/show state, initialized from the host and combined with document hidden/minimized state, to gate renderer countdowns, repaint and delta presentation. A blur alone is not hide. Preserve bounded cursor/anchor state, continue service collection and resync on show without replaying every hidden intermediate announcement. Recompute time-dependent display locally; do not poll quota. This implements §7.1 “while window visible”, §6.10 hide/restore and the plan's hidden-window bounds. Electron documents visibility caveats for initially hidden windows and disabled background throttling; do not generalize the brief's observation into a claim that every macOS window behaves the same. [Electron BrowserWindow: Page visibility](https://www.electronjs.org/docs/latest/api/browser-window/#page-visibility)
- **If DD1-02–04 are approved:** verify pending → success, known failure, connection loss with unknown outcome, reconnect and Close restoration; no duplicate mutation or false success. Verify native modality, first-field/Cancel focus, no backdrop dismiss, no destructive default submit, surviving/removed invoker restoration and an announced dialog-local result. Service-down behavior must preserve readable content and explain disabled writes.
- **If DD1-01/05–07 are approved:** cover named and unnamed fallback phrases, exact fixed labels and accessible names; selector group/body relationships and manual activation across wrapped lines; text-spacing overrides, 200% text, 320 CSS px, long escaped content and variable-height anchoring. Apply the existing both-theme viewport matrix and review actual renders/console before accepting baselines. A 65ch measure is not evidence of performance or readability until rendered.
- **All phases:** styles remain in the bundled same-origin stylesheet; no inline style block or style attribute is introduced, and dynamic offsets retain the approved CSSOM route. Every meaningful rendered pair must remain in §8.2. Keep native scrollbars available; test ring clearance instead of hiding overflow.
- **Runtime/fallback boundary:** proposed platform primitives are established HTML dialog/showModal, ordinary ARIA relationships, CSS ch sizing and existing flex/wrapping rules, supported by the specified Chromium target. No new experimental feature or polyfill is required. Newer closedby, command/commandfor, text-scale metadata, scroll-state queries and content-visibility are not requirements of this delta; do not silently substitute them. Verify behavior in the packaged Electron target rather than inferring it from a desktop browser.
- **Lint ideas only:** inspect token-only colors/fonts, instant focus, reduced motion, no transition: all or layout animation, no fake data, no Unicode icon substitutions, no hidden required narrow content and no decorative card/gradient pattern. These are manual review lenses here. Hallmark sloplint/render, screenshots, cache/stamp/preflight generation and automated pass/fail grades were not run or produced.
